Architecture Overview — Audit Log Service

This document is based on the implemented code and repository artifacts in the project, including the FastAPI application, database abstraction, Pydantic schemas, tests, and the generated smoke-test evidence.

1. Components

API layer
  • FastAPI application serving the audit endpoints.
  • Handles request validation and response shaping.
  • Applies lightweight security headers via middleware.
Domain logic
  • Computes the hash chain for each new event.
  • Replays the chain during verification.
  • Supports lifecycle and compliance operations over the same event records.
Persistence layer
  • Abstracts SQLite and PostgreSQL access.
  • Creates and initializes the audit table.
  • Uses the same event schema across both backends.
Validation and evidence
  • Pytest suite exercises core behavior and edge cases.
  • Smoke-test runner exercises the HTTP surface and produces HTML/markdown evidence.

2. Data model

The implemented data model is centered on a single audit_events table. The schema used by the service includes the following fields:
  • id: primary key
  • eventType, actorId, resourceType, resourceId: metadata describing the event
  • payload: the event payload stored as JSON text
  • timestamp: event timestamp
  • prevHash and currHash: hash-chain values used for integrity verification
  • status: lifecycle state, currently active or archived
  • redactedPayload, redactionVersion, redactionReason: metadata used for redaction support
The implementation uses the same logical shape for SQLite and PostgreSQL, with the main difference being the SQL dialect and the auto-increment strategy for the primary key.

3. API design

Core write/query flow
  • POST /audit/events: writes a new event.
  • GET /audit/events: lists events with optional filters and pagination.
  • GET /audit/verify: returns integrity status for the whole chain.
Lifecycle and review operations
  • POST /audit/events/{id}/archive: marks an event archived.
  • POST /audit/events/{id}/redact: stores a redacted payload copy and metadata.
  • POST /audit/events/retention/apply: archives older records based on an age threshold.
Export and compliance
  • GET /audit/export: returns matching records plus verification metadata.
  • GET /audit/compliance/report: returns a scoped summary by resource and actor.

4. Key decisions implemented

  • Monolithic service The implementation is a single FastAPI service rather than a distributed system, which keeps the prototype easy to run and review.
  • Append-only log model Events are written in sequence and retained as historical records.
  • Hash-chain verification Each event stores a prevHash and a computed currHash so tampering can be detected.
  • Metadata-based redaction Redaction is implemented by storing a redacted payload copy and version/reason metadata without rewriting the original chain.
  • Scoped compliance reporting Compliance reporting is intentionally lightweight and scoped by resourceId and actorId.
  • Lightweight security posture The app adds response headers such as x-frame-options, referrer-policy, and a CSP to support basic hardening.

5. Hash algorithm and chain design

The implemented hash design uses SHA-256. The hash input is built from a canonical JSON representation of the event content and the previous hash value. The first record uses the literal marker GENESIS as its predecessor, and each following record uses the previous record's currHash as the input for the next hash.
  • The current implementation computes the hash from the event fields: eventType, actorId, resourceType, resourceId, payload, and timestamp.
  • Verification walks the records in order and recomputes the expected hash for each row.
  • If any stored hash or predecessor value does not match, the service returns a verification failure with the first mismatch location.

6. Trade-offs and scope

  • Prototype scope: the service is intentionally lightweight and review-friendly rather than a production-grade compliance platform.
  • Verification vs prevention: the implementation detects tampering after the fact; it does not attempt to prevent unauthorized modification at the storage layer.
  • Redaction model: redaction is metadata-based and suitable for this prototype, but it is not a full immutable-history versioning model.
  • Storage choice: SQLite is the default runtime backend for simplicity, while PostgreSQL is supported through the database abstraction layer.
  • Compliance reporting: the report is scoped and summary-based, which keeps it reviewable but intentionally narrower than a full regulator-facing workflow.
